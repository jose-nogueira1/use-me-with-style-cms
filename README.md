# Use Me With Style -- CMS (Payload)

Backend data/admin-API layer for the Use Me With Style platform, per the
Phase 1 architecture decision (`docs/decisions/phase-1-architecture-and-blockers.md`
in `use-me-with-style-platform`, JOS-20): the existing React + Vite SPA stays
the storefront and admin UI; this service is Payload CMS + a database,
reached over REST/GraphQL.

## What's here

- **Products** -- catalogue, manual admin entry, per-market price (`priceAOKz`,
  `pricePTEur`) and **per-market stock** (`stockAO`/`stockPT` per size).
  *Flagged assumption:* the blueprint's Technical Appendix left "shared or
  separate AO/PT inventory" unresolved -- this defaults to separate. Confirm
  with Jay-P; collapsing to shared stock later is a smaller migration than
  the reverse.
- **Orders** -- the confirmed Phase 1 status pipeline (New, Payment Review,
  Processing, Shipped, Delivered, Cancelled), required checkout fields, and
  isolated payment paths: AppyPay/Multicaixa Express for Angola/Kz and
  Stripe/PayPal for EUR settlement. AppyPay webhooks are verified against the
  authenticated charge API before an order can become paid.
- **Customers** -- lightweight contact/order-history record, not a customer
  accounts system (accounts are Phase 2 per JOS-52).
- **Media** -- local-disk uploads by default (no cloud account needed for
  local dev); set `S3_BUCKET` (+ region/keys, see `.env.example`) to switch
  transparently to S3-compatible object storage (AWS S3, Cloudflare R2,
  Backblaze B2, DigitalOcean Spaces) via `@payloadcms/storage-s3` -- same
  "env decides, no code change" pattern as the Postgres/SQLite switch.
- **MarketSettings** (global) -- the one place to flip `angolaPaymentLive` on
  once SWEG/AppyPay is confirmed, and to fill in the returns policy text the
  blueprint appendix flags as still missing.
- **Messages** + `src/endpoints/messagingWebhook.ts` + `src/lib/messaging.ts`
  -- the Phase 1 WhatsApp/Instagram messaging automation **foundation**
  (JOS-58, narrowly scoped -- not a full AI agent, that's Phase 2/JOS-18):
  - `POST /api/messaging-webhook` receives inbound WhatsApp/Instagram
    messages from Meta, classifies them with simple keyword rules (order
    status / payment / delivery FAQ / sensitive-topic), auto-replies where
    it can (and only where it can -- unmatched or ambiguous messages are
    left "open" for manual review), and logs every message to the
    `messages` collection.
  - Sensitive topics (returns, complaints, refunds, cancellations) always
    escalate to a human and are never auto-resolved, per JOS-58 ("keep Raisa
    in control of sensitive or high-value conversations").
  - `src/hooks/notifyOrderEvent.ts` sends the order-confirmation/shipped
    WhatsApp notices (as before) and now also logs them to `messages`.
  - **Credentials needed to go live** (see `.env.example` for the full list
    with owners): `WHATSAPP_ACCESS_TOKEN`/`WHATSAPP_PHONE_NUMBER_ID`,
    `INSTAGRAM_ACCESS_TOKEN`/`INSTAGRAM_PAGE_ID`, `META_WEBHOOK_VERIFY_TOKEN`,
    `META_APP_SECRET`, and `INSTAGRAM_APP_SECRET` (validate signed inbound
    deliveries from both Meta login modes).
    Until set, sends log to the console instead of calling the Graph API --
    checkout and the webhook itself never fail because of this.
  - Admin view: "Mensagens" in the SPA admin (`use-me-with-style-platform`).

## Local development

No Docker or local Postgres install required -- leave `DATABASE_URL` as the
default `file:./dev.db` in `.env` and the config uses `@payloadcms/db-sqlite`
automatically. Point `DATABASE_URL` at a real `postgres://` connection string
(e.g. a Railway database) to switch to `@payloadcms/db-postgres` -- same
collections, same API, no code change.

```bash
cp .env.example .env   # then edit PAYLOAD_SECRET at minimum
npm install
npm run generate:importmap   # one-time: generates src/app/(payload)/admin/importMap.js
npm run dev             # http://localhost:3000/admin -- create your first user
npm run seed             # loads the prototype's product catalogue
```

REST API base: `http://localhost:3000/api` (e.g. `GET /api/products`).
GraphQL: `http://localhost:3000/api/graphql`.

## Note on this scaffold

This project was generated by hand against Payload 3.85.2's official
Next.js integration (the files under `src/app/(payload)/` are Payload's
standard generated routes, copied verbatim from the `blank` template) rather
than via `npx create-payload-app`, because the sandbox this was built in
resets its container between shell commands and can't sustain the
multi-minute `npm install` the CLI's own version check requires. **Verified
working 2026-07-07** (`npm install` + `npm run dev` + admin login all
confirmed on a real machine) -- if anything doesn't boot cleanly after a
dependency bump, most likely culprit is a version mismatch; keep the
`@payloadcms/*`/`payload`/`next` versions in `package.json` matching.
